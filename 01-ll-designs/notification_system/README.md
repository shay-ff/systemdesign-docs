# Notification System - Low Level Design

A multi-channel notification dispatcher (email / SMS / push) with a priority queue, per-channel rate limiting, exponential-backoff retries with a dead-letter log, and at-least-once delivery made safe by notificationId dedupe.

## Problem Statement

Design a notification service (think the engine behind "your OTP is...", "payment received", "order shipped") where:

- Business services publish notifications across **channels** - email, SMS, push - with per-channel formatting.
- Some notifications are **urgent** (OTPs, payment failures) and must jump the queue over bulk traffic (statements, marketing).
- Channel sends **fail transiently** (greylisted SMTP, throttled carriers); the system must **retry with exponential backoff**, and when the retry budget is exhausted, park the notification in a **dead-letter log** with its full attempt history.
- Vendors enforce **rate limits**; the system must throttle **per channel** rather than get 429'd vendor-wide.
- Delivery is **at-least-once**: workers can die after a send and brokers replay; the system must **dedupe by notificationId** so a user never gets the same OTP twice.
- Every notification's outcome is **observable**: QUEUED / SENT / FAILED / DEAD_LETTER / DUPLICATE / RATE_LIMITED.

## Key Features

- **Channel hierarchy**: abstract `Notification` with `EmailNotification` / `SmsNotification` / `PushNotification` - a **template method** for formatting (shared skeleton, channel-specific body + framing) and per-channel input validation.
- **Sender strategy per channel**: `NotificationSender` with deterministic mock implementations (`EmailSender` with a scripted attempt-failure list, `SwitchableSmsSender` with a runtime flippable "carrier down" flag, `PushSender` with a permanently dead token) - deterministic so the demo tells the same story every run.
- **Retry policy**: a reusable `RetryPolicy` (max attempts, exponential backoff with a cap, millisecond-scale for the demo) - injected, so channels can run different budgets without code changes.
- **Priority queue**: `PriorityBlockingQueue` ordered by `(priority rank, arrival sequence)` - HIGH first, then FIFO within a rank (the sequence tiebreaker is the detail interviewers miss).
- **Workers**: `ExecutorService` fixed pool polling the queue; per-channel **token-bucket rate limiting** defers over-budget sends (deferral, not failure).
- **At-least-once + idempotency**: dedupe at the **sink** (delivered-ids set) plus a cheap duplicate check at enqueue; the demo replays an already-delivered OTP and shows the sink dropping it.
- **Dead-letter log**: retries-exhausted and permanent failures land with reason + attempt history - the artifact ops greps at 2am.

## Clarifying Questions an Interviewer Expects You to Ask

1. **Delivery semantics: at-least-once or at-most-once?**
   At-least-once for anything that matters (OTPs, payments) - a missed payment alert costs more than a rare duplicate; duplicates are neutralized by notificationId dedupe. At-most-once (fire-and-forget) only fits lossy marketing spam, and even then you want the dead-letter log.
2. **How do you make at-least-once safe?**
   A stable **notificationId generated by the producer**, dedupe **at the sink** (after delivery, not at enqueue - the failure window is *after* a successful send), and consumers that treat duplicates as no-ops.
3. **Does priority preempt in-flight sends?**
   No - priority orders the QUEUE; a send already in flight completes. (True preemption means cancelling vendor calls - not worth it; say this out loud.)
4. **What happens to NORMAL traffic under sustained HIGH load?**
   Starvation - the honest answer. Fix with **aging** (wait time decays a notification's effective rank); see explanation.md for the sketch and why it is deliberately not implemented here.
5. **Retry immediately or back off?**
   Exponential backoff with a cap - a failing vendor is likely saturated; constant-interval retries are a self-inflicted DDoS.
6. **Is rate limiting per channel, per tenant, or global?**
   Per channel first (vendors throttle per API credential); per-tenant is the production follow-up. This system wires per-channel buckets; see `01-ll-designs/rate_limiter/` for the full rate-limiter treatment.
7. **Ordering within a channel - guaranteed?**
   No global ordering: workers run in parallel by design. Per-recipient ordering (if ever required) means a per-recipient queue with a single worker - a throughput trade-off; discuss rather than default into it.
8. **What happens when the process dies mid-flight?**
   The queued notifications are lost in this in-memory design - the production answer is a persistent broker (Kafka/SQS) whose redrive gives the at-least-once replay the demo simulates.

## Core Entities

| Entity | Responsibility |
|---|---|
| `Notification` (abstract) | Identity (notificationId), recipient, message, channel, priority, attempt count; template-method `format()`; guarded `overrideId`/`withId` replay seam |
| `EmailNotification` / `SmsNotification` / `PushNotification` | Channel variants: body formatting, framing hooks, per-channel validation (email `@`, phone digits, `device:` token) |
| `NotificationChannel` / `NotificationPriority` / `NotificationStatus` | Enums: EMAIL/SMS/PUSH; HIGH/NORMAL (queue rank); QUEUED/SENT/FAILED/DEAD_LETTER/DUPLICATE/RATE_LIMITED |
| `NotificationSender` (interface) | Per-channel send strategy: `send(notification)` throwing `SendException` |
| `EmailSender` / `SwitchableSmsSender` / `PushSender` | Deterministic mocks: scripted attempt failures; runtime-flippable carrier outage; a permanently dead push token |
| `SendException` | Carries `transient` vs `permanent` - transient retries, permanent dead-letters immediately |
| `RetryPolicy` | Max attempts + exponential backoff with cap (ms-scale for the demo); injected, reusable |
| `TokenBucketRateLimiter` | Minimal per-channel token bucket (burst + refill); the fuller reference is `../rate_limiter/` |
| `DispatcherService` | The heart: priority queue, worker pool, rate limiting, retry loop, sink dedupe, dead-letter log, outcome records |
| `NotificationAttempt` | Immutable one-attempt record (number, outcome, timestamp) - the attempt HISTORY the dead letter needs |
| `DeliveryOutcome` | Immutable terminal outcome + attempt list + detail; one-line summary for tables |
| `NotificationDemo` | Five-section end-to-end narrative demo |

## Design Patterns Used (and why)

- **Template method - Notification.format.** Header (To/Subject) + body + footer is shared framing; only the body and separators vary per channel. One framing change happens once, not three times; `final` prevents subclasses skipping the skeleton.
- **Strategy - NotificationSender per channel.** Email/SMS/push are different vendor integrations with different failure modes; the dispatcher knows "send this", never why SMTP greylists. Swapping a vendor = new implementation, zero dispatcher edits (OCP).
- **Observer-flavoured pipeline (producer -> queue -> workers).** Business services publish without knowing who consumes; the dispatcher subscribes workers to the same queue. The queue - not method calls - is the decoupling (and the durability seam in production).
- **Command-ish attempts.** Each `NotificationAttempt` is an immutable event appended to history; outcomes are foldable facts, not mutable state.
- **Dependency injection of policies.** `RetryPolicy` and per-channel limiters are injected into `DispatcherService` - changing budgets is configuration, not surgery.

## Time Complexity

- Enqueue: O(log N) (priority queue insert)
- Dispatch loop per notification: O(log N) dequeue + O(1) limiter + O(send)
- Dedupe checks: O(1) hash-set lookups
- Outcome recording: O(1) append

## Interview Extension Questions

1. How would you **persist** this? (Kafka/SQS as the queue; workers ack after send; redrive policy = the retry loop; dead-letter = the broker's DLQ.)
2. How would you prevent **starvation** of NORMAL traffic? (Aging: effective rank = base rank - waitedTime/coefficient; or separate queues + weighted round-robin.)
3. How would you add **per-tenant** rate limits? (A second limiter keyed by tenant; compose: channel bucket AND tenant bucket must both pass.)
4. How do you **guarantee per-user ordering** when needed? (Sticky routing: hash(userId) -> one worker; sacrifice parallelism per user, keep it globally.)
5. What observability do you add? (Per-channel SENT/DEAD_LETTER ratios, retry-attempt histograms, queue depth gauges - the `DeliveryOutcome` records are already the data.)
6. How do you handle **poison messages** (always 500 at the vendor)? (This design: retries exhaust -> dead letter; add a circuit breaker per channel when the failure RATE spikes - trips skip the queue entirely.)
7. **Fan-out**: one event to many channels? (One event -> N channel notifications sharing the source event id; dedupe stays per (channel, recipient).)
